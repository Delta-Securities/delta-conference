# Стандарт деплоя Delta Securities

Версия 1.1 от 24.09.2026. Библиотека `scripts/lib/ds-deploy.sh` версии 1.1.0.
Действует для всех репозиториев организации Delta-Securities. Факты конкретного проекта — в его `DEPLOY.md`.

## 1. Ветки и PR

- **Основная ветка** (`main` или `master`, не переименовываем) — это то, что работает на проде.
- Прямой push в основную ветку и в `develop` запрещён всем. Любое изменение: ветка → PR.
- **Есть `develop`** (только deltaprop и spread-arb): feature → PR в `develop` → полигон выкатывается сам. Релиз — PR `develop → основная ветка`. Хотфикс идёт тем же путём.
- **Нет `develop`** (все остальные): feature → PR в основную ветку.
- То, что после мержа `develop` «отстаёт» от основной ветки на merge-коммиты, — норма. Разницы в файлах там нет.

## 2. Мерж

Мержит только владелец, или Claude на его ПК по его прямой просьбе. Команда одна для всех PR:

```bash
gh pr merge <N> --repo Delta-Securities/<repo> --merge --admin
```

- Метод — только merge-коммит.
- Никогда: `--squash`, `--rebase`, `-d`/`--delete-branch` (удалит `develop`), `--auto`.
- Статус BLOCKED у PR в основную ветку — норма: правило ветки пропускает только админа организации через `--admin`.
- Мерж ничего не выкатывает на прод.

## 3. CI

- В каждом репозитории есть `.github/workflows/ci.yml` с job **`ci`**.
- `ci` — агрегатор. Он зелёный, только если все проверки из `needs` прошли: shellcheck скриптов деплоя, сборка, тесты и линт по стеку.
- Запускается на каждый PR и на push в основную ветку и `develop`, без фильтров по путям.
- Имя `ci` одинаковое везде. Владелец делает его обязательной проверкой в правиле ветки.
- Выкатить можно только коммит с зелёным `ci`: это проверяет сама команда деплоя. Проверка нужна потому, что админ может смержить и при красном CI.

## 4. Деплой

```bash
scripts/deploy.sh prod --dry-run   # всё проверить и показать; сервер не меняется
                                   # (цели со сборкой собираются на ПК — видно, что изменится)
scripts/deploy.sh prod             # выкатить; спросит имя репозитория (или --yes)
scripts/deploy.sh staging          # полигон (обычно выкатывается сам из Actions)
```

Запускается с ПК владельца: им самим или Claude по его прямой просьбе. Команда одинаковая во всех проектах. Она гарантирует:

1. **Что выкатывается.** Только `origin/<основная ветка>` (для staging — `origin/develop`), взятый после `git fetch`. Рабочая копия, текущая ветка и незакоммиченные правки ни на что не влияют.
2. **Чья логика.** Сам скрипт выкатки тоже берётся из этого коммита: он распаковывается во временный каталог и перезапускается оттуда.
3. **CI.** Нужен зелёный check-run `ci` у этого коммита, иначе отказ.
4. **Откуда код.** Только из `git archive` коммита (переводы строк LF). Никогда из рабочей копии.
5. **Маркер на сервере.** В каталоге проекта лежит `.ds-deploy/` с тремя файлами: `DEPLOYED` (какой коммит, когда, кто, итог), `MANIFEST` (sha256 каждого файла), `history`.
   - Нет маркера → отказ: сервер не мигрирован.
   - Файл изменён на сервере вручную (дрейф) → отказ со списком файлов.
6. **Что меняется на сервере.** Записываются только файлы, которые отличаются от выкатанных; остальные не трогаются вовсе (ни время, ни права). Записанным файлам ставится время «сейчас» — сборка на сервере (make/ninja) пересоберёт изменённое, и при откате тоже. Если файл на сервере был исполняемым, а в git лежит без `+x`, бит возвращается с предупреждением. Удаляются только файлы, которые убраны из git. Пути из `DS_PRESERVE`, `.env*` и ключи не трогаются никогда. Чужие файлы только перечисляются.
   - Файл **из git**, похожий на секрет (`.env.*`, `*.pem`, `*.key`, `credentials.json` …), — отказ: либо это утечка (убрать из git), либо не секрет (`DS_DEPLOY_SECRETLIKE` в `scripts/deploy.sh`), либо его не нужно выкатывать (`DS_PRESERVE`).
7. **Проверки перед стартом:** окно выкатки (МСК считается как UTC+3), свободное место на диске, лок на ПК и общий лок на сервере. Для prod нужно подтверждение (ждёт 5 минут). Окно проверяется ещё раз на сервере — прямо перед шагом `pre`, после подтверждения, сборки и ожидания лока.
8. **После выкатки** — проверка здоровья на сервере и, если она есть в проекте, с ПК. Итог `ok` пишется в маркер только после обеих; иначе `health-failed`. Итог есть и в журнале ПК `~/.delta-deploy/deploy.log`.
   - Если прошлая выкатка не завершилась успешно (`post-failed`, `health-failed`, …), следующая передаёт хукам все изменения с последней успешной (`MANIFEST.ok`), чтобы шаг `post` снова поднял остановленное.
9. **Как устроен код.** Все изменения на сервере идут через одну функцию `ds_run` (в `--dry-run` она только печатает). Все чтения идут через `ds_probe`. Используется одна SSH-сессия с keepalive.

Коды выхода:

| Код | Что значит |
|---|---|
| 0 | готово |
| 2 | в проекте нет деплоя (для `staging` — нет ветки `develop`) или ошибка в вызове |
| 3 | отказ по проверке, сервер не менялся |
| 4 | сбой посередине выкатки |
| 5 | код выложен, но проверка здоровья не прошла |

Флаги обхода. Каждый требует причину словами, она пишется в журнал. Использовать только по решению владельца:

| Флаг | Что делает |
|---|---|
| `--skip-ci "…"` | выкатить без зелёного `ci` |
| `--ignore-window "…"` | выкатить вне окна |
| `--overwrite-drift "…"` | перезаписать ручные правки на сервере; перед этим они сохраняются в `.ds-deploy/backup-*.tgz` |

Служебные флаги:

| Флаг | Что делает |
|---|---|
| `--adopt` | разовая миграция: ставит маркер, если сервер точно совпадает с коммитом; с `--overwrite-drift "…"` — заменяет отличающиеся файлы из git; у цели с `DS_ADOPT_MODE=replace` — записывает файлы из git сразу |
| `--adopt-sha <sha>` | то же для более старого коммита основной ветки. Если файлы не перезаписываются (только маркер), `ci` у этого коммита не нужен — у коммитов до стандарта его нет |
| `--rollback` | вернуть предыдущий успешный коммит |
| `--only <цель>` | выкатить только одну цель |
| `--wait-ci` | подождать завершения `ci` |
| `--test-ref <ветка> --dry-run` | проверить ветку PR против сервера до мержа (только чтение) |

## 5. Полигон

- Полигон есть только у deltaprop и spread-arb, на ВМ `staging.deltaprop.ru`.
- Как выкатывается: push в `develop` → `ci` → job `deploy-staging` в том же `ci.yml` (`needs: ci`). Он запускает `scripts/deploy.sh staging --yes --ci-from-needs`.
- Выкатку не прерывает новый push (`cancel-in-progress: false`).
- Ключ `STAGING_SSH_KEY` лежит в environment `staging`, туда допущена только ветка `develop`. Других секретов в GitHub нет.

## 6. Серверы

- Код попадает на сервер только командой `scripts/deploy.sh`. Руками файлы на серверах не правим: ни `scp`, ни `git pull`, ни правки «на месте».
- Если сервер расходится с основной веткой, нужна **разовая миграция** по письменному плану в `DEPLOY.md`. Выполняет её владелец (с Claude), для торговых систем — вне торгов. Порядок:
  1. `--dry-run` показывает расхождения;
  2. лишнее переносится в архив, расхождения — в git через PR;
  3. `--adopt` ставит маркер (или `--adopt-sha <sha>`, если сервер совпадает со старым коммитом основной ветки; для коммитов до стандарта `--skip-ci` не нужен).
  До миграции реальная выкатка отказывает.
- `DS_ADOPT_MODE=replace` (статика, которую не жалко перезаписать): на полигоне первая выкатка без маркера записывает файлы сама; на проде — только явно, `scripts/deploy.sh prod --only <цель> --adopt`.
- `--adopt` не меняет владельцев и права файлов: `DS_CHOWN` применяет первая обычная выкатка (и каждая следующая). Ручной `chown` в плане миграции не нужен.
- Скрипты, которые cron или systemd запускают напрямую, лежат в git с битом исполнения: `git update-index --chmod=+x <файл>` (на Windows бит сам не ставится).
- Хосты в скриптах указываются только DNS-именами. Отпечатки серверов закреплены в `scripts/lib/known_hosts`.
- Торговые системы (prop-core, hft-moex, prop-limits-monitor, а spread-arb — после появления живого исполнения) перезапускаются только в окне `DS_WINDOW`. Окно утверждает владелец.

## 7. Секреты

- SSH-ключи и секреты хранятся только на ПК владельца и на серверах (`.env`, права 600).
- В GitHub — только `STAGING_SSH_KEY`, новых секретов не добавляем.
- Скрипт не читает, не копирует и не печатает секреты. `.env.example` содержит только имена.

## 8. Откат

- Обычно: revert-PR → мерж → `scripts/deploy.sh prod`.
- Срочно: `scripts/deploy.sh prod --rollback` — предыдущий успешный коммит из истории сервера. Работает только если этот коммит входит в основную ветку.
- Миграции БД и данные откатываются по правилам из `DEPLOY.md` проекта.

## 9. Если выкатка не удалась

1. Прочитать вывод: причина напечатана в блоке «ОТКАЗ» или «НЕ ГОТОВО».
2. **Код 3.** Устранить причину (CI, окно, дрейф, диск) и повторить.
3. **Код 4.** Запустить `scripts/deploy.sh <env> --dry-run`. Он покажет состояние сервера, повторная выкатка того же коммита безопасна. Если прод сломан — `--rollback`.
4. **Код 5.** Проверить логи сервиса (команда есть в `DEPLOY.md`), затем `--rollback` или фикс через PR.
5. На сервере ничего не чинить руками. Если без этого никак, это решение владельца, и потом это оформляется PR и `--overwrite-drift`.

## 10. Правила для Claude (есть в каждом CLAUDE.md)

- Не пушить в основную ветку и `develop`, только PR.
- Мержить и выкатывать только по прямой просьбе владельца и только стандартными командами. Сначала `--dry-run` и показать его владельцу, `--yes` — только после его «да».
- Не выкатывать рабочую копию, ветку или отдельные файлы. Не править файлы на серверах. Не перезапускать сервисы руками. Не писать свои скрипты выкатки. Не редактировать `ds-deploy.sh`.
- Флаги обхода — только по прямому указанию владельца с его причиной.
- Отказ скрипта не обходить, а показывать владельцу.
- Секреты не читать и не выводить.

## 11. Состав стандарта в каждом репозитории

| Файл | Что это |
|---|---|
| `scripts/lib/ds-deploy.sh` | общая библиотека, побайтно одинаковая везде; CI сверяет её sha256 |
| `scripts/lib/DEPLOY_STANDARD.md` | копия этого стандарта, тоже одинаковая везде |
| `scripts/deploy.sh` | проектная часть: цели, `DS_PRESERVE`, окно, хуки перезапуска и здоровья |
| `scripts/lib/known_hosts` | отпечатки серверов проекта (если есть серверы) |
| `.github/workflows/ci.yml` | job `ci`, плюс `deploy-staging` там, где есть полигон |
| `DEPLOY.md` | факты проекта по шаблону |
| `CLAUDE.md` | одинаковый блок «Изменения и деплой» |
| `.gitattributes` | `*.sh text eol=lf` |

Исполняемые скрипты (`deploy/*.sh` для cron и systemd, `ExecStartPre` и т.п.) — в git с режимом `100755`: `git ls-files -s <файл>` показывает режим, `git update-index --chmod=+x <файл>` его ставит.

**Новая версия библиотеки.** Правится только в эталоне стандарта. Затем PR во все репозитории: сам файл, этот стандарт, sha256 библиотеки в `ci.yml` и поле «Версия» в `DEPLOY.md`.

**Новый репозиторий:**
1. ruleset `default-branch-only-via-PR` с обязательной проверкой `ci`;
2. разрешён только merge-коммит;
3. все файлы из таблицы выше;
4. PR со стандартом смержен до первой выкатки.
